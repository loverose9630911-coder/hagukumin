## 3. 何を作ったか

### 画面

| 画面 | できること |
|---|---|
| ダッシュボード | 左に自分、右にチームを同じ並びで表示。残タスク・遅延・完了率・負荷・目標の進捗 |
| ボード | カンバン。ドラッグでステータス変更。**担当者ごとの列**にも切り替え可能 |
| テーブル | Notionのデータベース表示にあたるもの。検索・絞り込み・並べ替え |
| 目標 | 目標値と期限の進捗。チーム目標と個人目標を同じゲージで並べる |
| チャンネル | Slackのような会話。タスクのスレッドも同じ流れに出る |
| チーム設定 | 参加コード・メンバーの「1週間に使える時間」・プロジェクト管理 |

### 数字の意味を4つに絞った

これは説明のときに強い武器になります。「**この4つだけ覚えれば全部読めます**」と言えるからです。

| 言葉 | 定義 |
|---|---|
| 残り | 完了していないタスク |
| 遅れ | 納期が今日より前で、まだ完了していないタスク |
| 負荷 | 残タスクの見積工数 ÷ その人が1週間に使える時間 |
| 進捗 | 実績値 ÷ 目標値 |

> 「ダッシュボードって、指標を増やせば増やすほど誰も見なくなるんですよね。
> なので**意図的に4つに絞って**、全部の画面をこの4つの組み合わせだけで説明できるようにしました。」

## 4. なぜ作ったか（きっかけ）

### 構造としての課題（ここは事実として話せます）

> 「タスク管理ツールと連絡ツールが別々だと、3つの問題が起きます。
>
> 1つめは、**タスクの場所とその話をした場所が離れる**こと。
> 『あの件どうなった』がSlackで流れて、Notionには反映されないまま埋もれます。
>
> 2つめは、**報告のための報告が発生する**こと。
> タスクを進めたあと、わざわざ『進めました』と別の場所に書く手間が二重にかかります。
>
> 3つめは、**個人の数字とチームの数字が別々に管理される**こと。
> 個人目標とチーム目標を別々の表で持つと、合計が合わなくなっていきます。」

### ここに、ご自身の体験を足してください

上の3つは「一般論としての課題」です。面接で効くのは、**そこにご自身の実感が乗ったとき**です。

書き足すときのヒント：

- どんな場面で困ったか（例：週次の進捗会議、目標の締め、誰かの抱え込みに気づけなかった）
- そのとき何が見えていなかったか
- 「これが見えていれば」と思った具体的な数字は何だったか

> 記入欄：
>
> 「私は〈　　　　の場面〉で、〈　　　　が見えないこと〉に困っていました。
>  とくに〈　　　　〉が分からないまま進んでしまうことが多く、
>  『〈　　　　〉が一目で分かれば』とずっと思っていたのが出発点です。」

**注意：** ここを作り話にすると、深掘りされたときに必ず崩れます。小さくても実際にあった話にしてください。「前職で」でなくても、「学習会の進捗管理で」「家族の予定管理で」でも十分成立します。

## 5. 語れる設計判断 3つ

技術面接で効くのは機能一覧ではなく**「なぜそうしたか」**です。この3つを用意しておけば、たいていの深掘りに答えられます。

### 5-1. プロジェクト＝データベース＝チャンネル

```
        プロジェクト「新規開拓」
        ├─ タスク一覧（Notion のデータベース）
        └─ 会話          （Slack のチャンネル）
```

> 「この2つを別々のテーブルにすると、必ず『どのタスクの話か』が迷子になります。
> なので**同じIDで束ねました**。メッセージは必ずプロジェクトに属していて、
> `task_id` が入っているものは『そのタスクのスレッドの発言』として扱われます。
> プロジェクトを1つ作れば、タスク置き場とチャンネルが同時にできる、というのがこの設計の効果です。」

**深掘り対策：** 「分けたほうが柔軟では？」と聞かれたら
→ 「柔軟にはなりますが、その柔軟性は今回いらないと判断しました。小規模チーム向けなので、選択肢を減らして迷わせないほうが価値が高いと考えています。」

### 5-2. 自分とチームを「同じ関数」で計算する

これは**いちばん語れるポイント**です。

> 「ダッシュボードの左が自分、右がチームなんですが、
> この2つは `Metrics::personSummary()` という**同じ関数**で計算しています。
>
> なぜかというと、別々に書くと必ずズレるからです。
> たとえば『完了率』を、自分側では完了タスク÷全タスクで、
> チーム側ではうっかり完了タスク÷未完了タスクで計算してしまったとします。
> 見た目には両方それらしい数字が出るので、**間違いに気づけません**。
>
> 同じ関数を通していれば、少なくとも『同じものさしで比べている』ことは保証されます。
> 可視化って、数字が間違っていても綺麗に表示されてしまうのが怖いところなので、
> そこは構造で防ぐようにしました。」

**この話が強い理由：** 「バグを見つけて直した」ではなく「**バグが起きない構造にした**」という話だからです。設計の話として一段上に聞こえます。

### 5-3. 目標に「予定線」を引く

> 「目標のゲージに、細い縦線を1本引いています。
> これは『**期限までの日数から見て、いま何％まで進んでいるべきか**』です。
>
> 『40%終わりました』だけだと、早いのか遅いのか分からないんですよね。
> 期限まで残り8割あるなら順調だし、明日が期限なら大問題です。
> **進捗率は、期限と並べて初めて意味を持つ**と考えて、この線を足しました。
>
> 塗りが線より右なら予定より早い、左なら遅れとして赤くしています。」

## 6. 難所と、どう乗り越えたか

### 6-1. チーム目標と個人目標が、別々の数字になってしまう

**状況**
最初の設計では、目標にタスクを紐づけて実績を合計する形にしていました。
ところが1つのタスクは1つの目標にしか紐づきません。
「チームの受注1,200万円」と「田中さんの受注400万円」を両方作ると、
**タスクをどちらに紐づけても、もう片方が0のまま**になってしまいました。

**何が問題か**
これは表示のバグではなく**モデルの問題**です。
現実には「チームの数字は個人の積み上げ」なのに、データ構造がそれを表現できていませんでした。

**どう考えたか**
最初「タスクを複数の目標に紐づけられるようにする」ことを考えましたが、やめました。
二重計上が起きやすく、使う人が正しく使うのが難しくなるからです。

代わりに、**目標そのものに親子関係を持たせました**。

```
今期の受注金額  1,200万円（チーム目標）
  ├ 田中  400万円（個人目標）
  ├ 佐藤  350万円
  ├ 鈴木  250万円
  └ 高橋  200万円
```

**どうしたか**
`goals` テーブルに `parent_id` を足し、集計を3周に分けました。

1. タスクから決まる目標を先に計算する
2. 子（個人目標）の実績を親（チーム目標）に足し上げる
3. 合計が出そろってから達成率と「予定より早い/遅い」を出す

制約も入れました。**親はチーム目標のみ・子は個人目標のみ・親子は1段まで**。
無限にネストできると、集計が循環したり誰も理解できない構造になるからです。

**学んだこと**

> 「表示がおかしいときに、表示を直すのか構造を直すのかの判断だと思っています。
> 今回は『チームの数字は誰の積み上げか』という**業務上の意味**がモデルに無かったのが原因だったので、
> テーブルに1列足すところまで戻りました。
> 結果的に、チーム目標のカードに『誰がどれだけ積んだか』がそのまま並ぶようになって、
> **直したら機能が良くなった**というのが気持ちよかったです。」

### 6-2. 無料プランではディスクが使えない

**状況**
公開しようとRenderでBlueprintを適用したところ、赤いエラーで止まりました。

```
A Blueprint file was found but then there was an issue.
disks are not supported for free tier services
```

**何が問題か**
SQLiteのファイルを残すためにディスクを付けていたのですが、**無料プランではディスクが使えません**。
つまり「データを残す」と「無料で公開する」が両立しない、という制約に突き当たりました。

**どう考えたか**
ここは技術ではなく**判断の問題**だと切り分けました。

| | 無料プラン | 有料プラン（月7ドル程度） |
|---|---|---|
| ディスク | 使えない | 使える |
| データ | 起き直すたびに消える | 残る |
| 用途 | お試し・デモ | 実運用 |

今回の目的は「まず動くものを見せる」だったので無料プランを選びました。

**どうしたか**
ただしディスク無しには落とし穴があって、**眠って起き直すたびに中身が空になる**ので、
そのままだとログイン画面で誰も入れなくなります。

そこで、`MIKATA_SEED=1` という環境変数を渡したときだけ、
**中身が空のときに限って**デモデータを入れてから起動する仕組みを足しました。
すでに誰か登録していれば何もしません。

```
中身が空 + SEED=1        → デモデータを入れて起動
既にデータあり + SEED=1  → 何もしない（上書きしない）
SEED なし                → 何もせず起動（実運用向け）
```

3パターンとも実際に動かして確認しました。

**学んだこと**

> 「制約に当たったとき、技術的に突破しようとするんじゃなくて
> 『**今回の目的なら、どちらを捨てていいか**』を先に決めたのが良かったと思っています。
> 無料プランを選んだうえで、その選択の副作用（データが消える）に対して
> 手当てを入れた、という順番です。
> 有料に切り替える手順も設定ファイルにコメントで残してあるので、必要になったら3行変えるだけです。」

### 6-3. Dockerのビルドが必ず失敗する（★いちばん語れる難所）

**状況**
Blueprintは通ったのに、今度は**2つのサービスが両方とも Failed deploy** になりました。

**どう切り分けたか**
まずログを見たかったのですが、手元の環境からはRenderに接続できませんでした。
そこで**手がかりから絞り込む**方針に切り替えました。

いちばん効いたのは「**両方**失敗している」という事実です。
2つは別のアプリで、Dockerfileも中身が違います。
それでも両方落ちているなら、**共通している部分が怪しい**。

差分を取ると、共通していたのはこの1行でした。

```dockerfile
docker-php-ext-install ... pdo_sqlite
```

**どう確かめたか**
推測で直すと外したときに時間を無駄にするので、**一次情報を取りに行きました**。
公式PHPイメージの定義（docker-library/php）を実際にcloneして中を読んだところ、
決定的な事実が2つ見つかりました。

| 場所 | 内容 |
|---|---|
| 154〜156行目 | PHP本体が `--with-pdo-sqlite=/usr` でビルドされている＝**最初から組み込み済み** |
| 108行目 | 再ビルドに必要な `libsqlite3-dev` は、ビルド後に `apt-get purge` で**削除されている** |

つまり、

> **「すでに入っているものを、材料が無い状態で作り直そうとしていた」**

これなら必ず失敗しますし、両方のDockerfileに同じ行があったので2つとも同じ場所で落ちていた説明もつきます。

**どうしたか**
その行を消しただけでは「たぶん直った」で終わってしまうので、
代わりに**ビルド時に確かめる行**を入れました。

```dockerfile
RUN php -m | grep -qx pdo_sqlite \
 || { echo "pdo_sqlite が見つかりません。ベースイメージの構成が変わった可能性があります" >&2; exit 1; }
```

こうしておくと、将来ベースイメージの構成が変わったときに、
黙って動かなくなるのではなく**その行ではっきり止まって理由が出ます**。

**結果**
マージ後の1回目のデプロイで通りました。あとから履歴を見たら、

```
3:30 PM  ❌ Deploy failed  — Exited with status 1 while building your code
3:45 PM  🟢 Deploy live
```

失敗のほうに「**while building your code**（ビルド中）」と明記されていて、
切り分けが合っていたことが裏づけられました。

**学んだこと**

> 「ログが見られない状況だったので、**共通点から攻める**という切り分け方をしました。
> 『2つとも落ちているなら、違うところじゃなくて同じところが怪しい』という発想です。
>
> それと、推測で直さずに公式イメージの定義を実際に読みに行ったのが良かったと思っています。
> 読めば5分で確定する話を、勘で3回試すと1時間かかりますし、
> 直っても『なぜ直ったか』が分からないままになります。
>
> あと、直すときに『消す』だけじゃなく『**次に同じことが起きたら気づける形**』にしたのが
> 自分の中では一番の学びでした。」

### 6-4. 完了したタスクが「遅延」と赤く表示されていた

**状況**
ボード画面を実際に動かして見ていたとき、完了済みのタスクに
「8/20（9日おくれ）」と**赤い表示**が出ているのに気づきました。

**何が問題か**
テストは全部通っていました。集計ロジックとしては正しく、
納期を過ぎていることも事実です。しかし**もう終わっているタスクを急かす意味はありません**。

これは「ロジックのバグ」ではなく「**意味のバグ**」でした。

**どうしたか**
納期の表示を出す関数に「完了しているか」を渡すようにして、
完了済みなら赤くせず、日付だけを淡色で出すようにしました。
ついでに、担当者別のボードではステータスが分からなくなっていたので、
そこにステータスの札を出すようにもしました。

**学んだこと**

> 「テストが全部通っていても、実際に画面を見ないと分からない種類の問題がある、というのが学びでした。
> なのでこのプロジェクトでは、テストとは別に**ブラウザで実際に動かす確認**を12件用意して、
> 明るい/暗いテーマ、スマホ幅、コンソールエラーの有無まで見るようにしています。」

## 7. 品質をどう担保したか

### テスト102件は「集計」に集中させた

> 「テストを書く場所を選ぶとき、**間違っても気づきにくいところ**を優先しました。
> 画面のボタンが押せないのはすぐ気づきますが、
> **完了率が5%ずれていても誰も気づかない**んですよね。
> なので集計ロジックにテストを寄せています。」

とくに見ているところ：

- 納期の分け方（遅延／今日／3日以内／それ以降／なし）と、**その境目の日**
- 完了率・負荷（未完了の見積だけを数えているか）
- **使える時間が0のとき、目標値が0のときに落ちないか**（ゼロ除算）
- 目標の4通りの数え方と、親子の積み上げ
- チーム外の人が見られない・担当にできないこと
- ステータスを変えるとスレッドに1行流れ、メモだけの変更では流れないこと

**深掘り対策：** 「カバレッジは？」と聞かれたら
→ 「率は測っていません。今回は率を上げることより『ズレても気づけない箇所を潰すこと』を優先しました。逆に画面の見た目のテストは書いていなくて、そこはブラウザでの確認12件に任せています。」

### セキュリティ

小さなチーム向けですが、公開する以上の最低限は入れています。

- パスワードは `password_hash()` で保存
- セッションは64桁のトークンを HttpOnly / SameSite=Lax の Cookie で保持
- SQLはすべてプレースホルダ（SQLインジェクション対策）
- 画面の文字は `textContent` で入れる（`innerHTML` 不使用＝XSS対策）
- 更新系の通信には独自ヘッダを要求（CSRF対策）
- **チームのデータは `Api::teams()` の1か所で必ずメンバー確認を通す**

最後の項目は5-2と同じ考え方です。

> 「権限チェックを各APIに書くと、**1か所書き忘れたら穴が空きます**。
> なので、チームに属するデータへの入口を1本にまとめて、
> そこを通らないとデータに触れない構造にしました。」

## 9. 想定質問と答え方

**Q. なぜPHPなんですか？**
> 「同じリポジトリに既存のPHPアプリがあって、構成を揃えたかったのが一番の理由です。
> あとは、ビルド工程なしで1コマンドで動かせるのが今回の目的に合っていました。
> 言語ありきではなく、置き場所の制約から選んでいます。」

**Q. なぜSQLite？PostgreSQLでは？**
> 「利用者が5〜30人想定なので、SQLiteで十分と判断しました。
> バックアップがファイル1つのコピーで済むのも、運用する人が非エンジニアの場合に効きます。
> ただし同時書き込みが増えたら限界が来るので、そこはPostgreSQLに移す前提です。
> 書き込みは全部リポジトリ層に閉じてあるので、移行は現実的な範囲だと思っています。」

**Q. リアルタイム更新はWebSocketではないのですか？**
> 「5秒おきに『前回以降の差分だけ』を取りに行くポーリングにしています。
> WebSocketのほうが望ましい場面は多いのですが、今回は
> **置き場所を選ばないこと**を優先しました。
> 5秒の遅れが問題になる用途ではないという判断もあります。」

**Q. これを10倍の規模にするなら？**
> 「3段階あると思っています。
> まずPHPの内蔵サーバーをnginx + php-fpmに置き換える。これはアプリ側の変更が要りません。
> 次にSQLiteをPostgreSQLに移す。
> 最後にポーリングをWebSocketかSSEに置き換える。
> 今の作りだと、この順番で必要になった分だけ変えられるはずです。」

**Q. 次に何を足しますか？**
> 「本物のNotionとSlackとの同期です。
> タスクの変更もチャットの投稿も、それぞれ入口を1本にまとめてあるので、
> そこに外部への送信を足す形で入ります。
> 機能としては、繰り返しタスクとファイル添付、あとは通知ですね。」

**Q. うまくいかなかったこと・反省点は？**
> 「Dockerfileの `pdo_sqlite` は、最初に公式イメージの構成を確認していれば
> 書かなかった行でした。**動くだろうと思って書いた**のがそのまま失敗になっています。
> 手元でDockerを動かせない環境だったので、確認が後回しになったのも理由の一つです。
> 今は、確認できない環境で書くときほど**ビルド時に自己検証する行を入れる**ようにしています。」

この質問には**必ず用意しておいてください。** 素直に失敗を語れる人は評価されます。

## 10. AI活用について聞かれたら

このアプリはAI（Claude Code）を使って開発しています。**聞かれたら正直に答えてください。**
隠すとリスクになりますが、正直に話せば**むしろ加点される話**です。

### 話し方の例

> 「開発にはAIコーディングツールを使っています。コードの多くはAIが書きました。
>
> ただ、**何を作るか・どう作るかを決めたのは私**です。たとえば
> ダッシュボードを『左が自分・右がチーム』に割ると決めたこと、
> 数字の定義を4つに絞ったこと、目標に親子関係を持たせると判断したこと、
> 無料プランを選んでデータを捨てると決めたこと。
> ここは全部、私が要件と目的から判断しています。
>
> あと、**出てきたものをそのまま受け入れない**ようにしていました。
> 実際に画面を触って『完了したタスクが赤く遅延表示されている』のを見つけて直しましたし、
> 表記がひらがな中心で業務アプリらしくなかったので、全部漢字に直させています。
>
> AIを使うと速く作れますが、**何が正しいかを判断するのは使う側**だと思っています。」

### この答えが効く理由

- 事実なので、深掘りされても崩れない
- **判断した箇所を具体的に3つ以上言える**ので、丸投げではないことが伝わる
- 「出てきたものを検証した」実例（6-4、表記の修正）があるので、批判的に見る姿勢が示せる

### やってはいけないこと

- 「全部自分で書きました」と言う → 一箇所でも突っ込まれると全部の信頼を失います
- コードの中身を説明できないまま提出する → **最低限、6章の難所は自分の言葉で説明できるようにしてください**
